codec/frame-rate/bit-depth/preset. AutoRun also unconditionally changes eight

but source alone does not prove which mismatch causes each observed artifact.

actual mode identity, geometry rebuild and stock restoration must be coherent.

HIGH-SPEED CLAIM, PRIMARY SOURCE CHECKED
Sony IMX410CQK flyer explicitly lists readout mode16: 2020x96, RAW12,
1628.22fps. The Sony readout-mode numbering is NOT SIGMA logical mode IDs.
https://www.sony-semicon.com/files/62/pdf/p-13_IMX410CQK_Flyer.pdf
The fp's 70 extracted logical entries have a minimum height672 and maximum
table fps239.76024. They do not contain the 96-row/1628fps configuration.
Unlocking it would need new register/receiver/buffer/recording integration.
The fp sensor variant's support also needs verification; the flyer is not a
camera specification.

At2020x96 RAW12 and1628.22fps, packed raw throughput is473.6166MB/s.
Two seconds requires947.2333MB of raw storage before padding, descriptors,
queues and camera working memory. Available safe capture RAM is not known.
An allocator argument of -1 is not proof all physical RAM is free or usable;
its actual API semantics and pool limits must be traced. Memory-side cropping
may reduce stored data but cannot reduce traffic already read from the sensor.
Programmable sensor-side horizontal cropping is not established here.
VMAX tuning changes frame period within valid sensor timing constraints; it
does not allow arbitrary fps or eliminate line-readout limits.

COMPRESSION CLAIM
Upstream identifies a fixed-function lossless JPEG engine at0x300D0000 used
for stills. That establishes a hardware engine, not necessarily a separate
physical chip. projects/raw-sup.md:37-78 explicitly leaves sustained throughput
unmeasured; ~300Mpixel/s is an estimate, not verified500MB/s performance.
Compression ratio depends on scene/noise and encoding throughput still matters.
Do not promise compressed high-speed video or size a RAM burst using an assumed
constant lossless ratio.

SAFETY AND AUTHOR CONTEXT
Author reports a service SD-to-RAM execution mechanism, AI-assisted decompilation
and a gyro writer based on audio-recording architecture. That is author
provenance, not evidence all generated explanations are correct.
Why SIGMA shipped the service entrypoint is unknown: call it a service mechanism,
not a proven developer mistake or intended public extension API.
Author reports no known bricking cases, no ROM writes in fpSup-Gyro, and removal
of the battery for10seconds as an effective full reset. Preserve the qualifiers:
this is not zero-risk proof and cannot be generalized to arbitrary future code.
Remove the boot payload before rebooting to stock; warm off/on can preserve RAM.
Manual-lens gyro logs reportedly work with zero lens metadata; select/calibrate
a matching Gyroflow lens profile. Do not treat a zero profile as calibrated.

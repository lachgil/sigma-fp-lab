SIGMA fp Ver.5.02 research map, reviewed 2026-09-11

Addresses use MAIN load base 0xC0000000 and reference SHA-256
92a8ee993f6c3d66c251e88d45a2ccd5135c6cf7342717784321c2ed506e2fb4.
Static evidence establishes instructions/data, not successful camera behavior.
See STATUS.md for hardware observations and GREEN-HOOK.md for reviewed traces.
No full decompilation or complete subsystem implementation is claimed.

TOOL LIMITS
fwmap.py scans whole words for candidate BL edges/prologues/literal addresses.
It can mistake data for code, misses indirect calls and movw/movt references,
and is not a complete control-flow graph. af_dis.py's movw/movt scan retains
register values across intervening instructions; confirm candidates by local
disassembly. Missing xrefs do not prove a table or function dead.

1. GEOMETRY: THREE DIFFERENT LAYOUTS

Manager getter 0xC0436590 returns M=0xC375D840 at 0xC0436600.
Live-state getter 0xC04376E0 returns O=*(M+0x0C).
MovSigProcess sequence 0xC0428B18..20 stores O at context+4.
O+4 is a DESCRIPTOR POINTER D, not a height. O+0 is used as state; O+0x58
participates in virtual dispatch. Never copy width/height into O+0/+4.

Extent getter 0xC0435858:
  x = D[+0xD8] if nonzero else D[+0x0C]
  alignment = 4 if D[+0x80] in {0xA,0xB,0x1000A}, otherwise 8
  result = round_up_u32(x, alignment)
Extent getter 0xC04358D0:
  y = D[+0xE0] if nonzero else D[+0x10]
  result = u32(y + D[+0x88] + D[+0x8C])
0xC0436304..08 follows O+4 then loads a float from D+0x30.
These are instruction-derived extents; units and format names are unresolved.

0xC04371F0 is NOT a simple record-geometry getter. It tests the object at
M+0x10, obtains/caches an allocation through 0xC001D038 at M+0xF8 (pool 5) or
M+0xE8 (pool 3), and returns it at 0xC0437380..88. MovSigProcess stores the
result at context+8. This is not proven to have the live object's layout.

Separately, geometry logger 0xC031D988 calls 0xC04370E8 with an output holder.
The returned aggregate has consecutive 0x58-byte blocks. Logger loads ground:
  block+0x00/+0x04 sizes; +0x20 raw_bit; +0x48/+0x4C rwzm; +0x50/+0x54 bin.
The second block starts at aggregate+0x58, NOT M+0x58 and NOT O+0x58.
Aggregate builder calls 0xC0437618, 0xC04375C8, 0xC0438B18, 0xC04386B0,
0xC0438828; ownership and lifetime still need tracing.

2. GREEN: RECORD-TIME MONITOR (live-confirmed root cause, session 2)

Live shell reads during a take (other dev, corroborated by this review's offline
accessor trace) resolve the green far past the session-1 uncertainty:
- Green is RECORD-TIME MONITOR ONLY. Live view is clean and the recorded DNG
  files are correct open gate. It is cosmetic LCD/HDMI framing during recording.
- During record, O=*(M+0x0C) points at a node whose selector word O+0x00 == 175.
  Its sub-object at O+0x5C is otherwise 3:2 (3032x2012 / 3008x2000) except a
  STALE FHD 16:9 pair at sub+0x0C/+0x10 = 1936x1090. 16:9 content in a 3:2
  monitor canvas leaves unwritten top/bottom bands that render green.
- The 0xC375Exxx node addresses are DYNAMIC; the manager cycles them per state.
  Gate on the node selector O+0x00 == 175, never a fixed node address.

Why a poke does not hold (also matches the session-1 no-visible-effect result):
poking sub+0x10 reverts every frame, and forcing 3032x2012 through the per-frame
accessor 0xC04376E0 overscans because the monitor BUFFER is allocated 16:9 at
record start. A correct fix hooks the record-start buffer/geometry build, follows
[M+0x0C] dynamically and is gated on selector 175, not the per-frame accessor.

Two distinct display paths, do not conflate them:
- STANDBY / live-view canvas: accessor 0xC0437E98 (indexed: returns *(obj+idx*8)).
  FP3K 0.3.5 fixes this with a gated accessor-return substitution returning a
  1620x1080 (3:2) descriptor for objects 0xC375EB68/0xC375ED3C. See build_greenfix
  and GREEN-HOOK.md. This review independently disassembled 0xC0437E98 and decoded
  that handler: it is FNV-1a fingerprinted on the object's 44-byte head, so a unit
  whose object differs safely passes through (no fix, no harm). Confirm the
  fingerprint on THIS unit before relying on it.
- RECORD monitor: accessor 0xC04376E0 (*(M+0x0C)) into MovSigProcess 0xC0428B18
  and YUV builder 0xC042A570. Needs the record-start buffer hook above; the
  standby fix is marginal here.

The earlier YuvResize attribution stays corrected: C03CB090 is a BL within
C03CB070, whose YuvResize label C0BA4298 sits among CinemagraphCreator.cpp source
strings. It is not the live-preview producer. inspect_preview.py reports the node
selector, the O+0x5C record-monitor fields and the descriptor extents from a
documented capture base; the current 1KB capture stops before O and says so.

5. HIGH FRAME RATE: SENSOR TABLES, NOT MEASURED FILE CADENCE

Picker tables C0BE5810/C0BE59B0/C0BE5B50: 26 entries, stride0x10, mode-id+8.
Known table-derived candidates (fps model assumes upstream 72MHz clock):
  slots0..3:   6064x3412 at29.97/25/24/23.976
  slots4..10:  3032x1708 at59.94/50/48/29.97/25/24/23.976
  slot11 M58:  3032x1708 at119.88; slot12 M89 at100
  slots13..16: 4176x2174 at29.97/25/24/23.976
  slots17..23: 2088x1174 at59.94/50/48/29.97/25/24/23.976
  slot24 M103: 2088x1174 at119.88; slot25 M118 at100

User reports stock 100/120fps choices in MOV, not CinemaDNG. Shared tables do
not prove these are hidden, otherwise-complete CinemaDNG modes.
Builder experiments: slot4 M27->M58; slot17 M88->M103. M58 was read back after
a take; unique-frame cadence, actual file geometry and sustained rate unverified.
No runtime version guard or USB shell in these standalone HFR AutoRuns.

Raw packed sensor-rate formula W*H*12/8*fps is not the recorded data rate when
scaling, borders or packing differ. Calculate storage requirements from actual
file bytes/frame and measured fps; no guaranteed SD/SSD rate has been measured.
Early recording stop is compatible with overflow but does not prove it.
Strings eMOVREC_STOP_OVERFLOW C0B9F0C6, OVERTIME C0B9F0AE, FAT C0B9F0DE identify
possible reasons, NOT live status registers. Do not poll those strings as flags.
No usable video RAM-burst implementation was found; absence is not proven.
Sony IMX410 mode numbers are not SIGMA mode IDs. See MODES.txt and original
Sony flyer link in DISCORD-FINDINGS.txt for the 96-row high-speed distinction.

7. LOADING, INTEGRATION AND FLASH

AutoRun shell path: XC_ShellScriptAutoRun C0BABE0C, code C03DA3F8, reader C03DA758.
fpSup gyro base loader uses cave C072DE64, USER allocation via bufmem,
VSHL.BIN sections, stage2 cache operation C000E91C. See pinned upstream source.
Do not combine loaders/caves by concatenating AutoRuns. Shell helper payloads
can overlap open-gate code. Cache coherence matters when replacing instructions.
Reviewed host toggle leaves the cold-boot branch installed and changes data only.

Stage3 integrated menu/loader is a DESIGN, not implemented. Build-time MAIN
hash checking does not verify the firmware of the camera booting an AutoRun.
Missing crypto symbols and detected checksums do not prove arbitrary updates
are accepted or that an earlier boot stage lacks authentication. No verified
recovery route or replacement-firmware acceptance test exists. Do not flash.

AfMgr, LmountFocusL/Mc/None and SAF/CAF are research leads in AUTOFOCUS.md.

INTEGRATION RULE
Keep source geometry, descriptor extents, allocations, recorded output and UI
state distinct. A matching table value, an assembling draft or a metadata tag
is not end-to-end proof. Record observations, their timing and capture provenance
before turning them into patch assumptions. No shared root cause across green,
darkness and playback has yet been demonstrated.

9. NATIVE CONTROL ARCHITECTURE, 2026-09-26

Goal: recover reusable native interfaces, not replicate a histogram/LUT feature.
The first bounded map below covers framework/recMgr/CameraFunction.cpp, named by
the original assertion string at C0B9DF18. It is not a global firmware event bus.

Producer -> owned envelope -> queue -> consumer policy -> method -> completion:
  C03A0798(manager, request)     native submission, not just a boolean event post
  C0B9E034                      51 indexed entries, IDs 0..50, 16 bytes each
  manager+128                   queue wrapper used for send/receive
  manager+12C                   synchronous completion flag wrapper
  C03A34A8                      consumer loop; receive, policy, dispatch, cleanup
  C03A3398                      dispatch one request through the metadata table
  C03A2438                      consumer-side camera-state policy

Metadata entry {id, this_adjustment, dispatch_kind, target}:
  kind == 0: disabled
  signed kind < 0: direct function target
  positive kind: virtual slot index; target becomes the vtable-pointer offset
All 51 original entries have zero this-adjustment and kind 0 or FFFFFFFF.
Virtual routing is instruction-derived, not exercised with a stock entry.
IDs 0,16,37,40,44,47,48,49,50 are disabled. Numeric IDs are local to this manager.
The table is indexed before bounds validation: it is NOT safe to fuzz IDs live.

Submission owns a 0xC0-byte envelope and copies exactly 0xBC request bytes into
envelope+4. It is a SHALLOW copy: pointer payloads do not gain lifetime ownership.
request+0 is the event ID; request+4 is an asynchronous byte. Other fields are
event-specific and are not all decoded. Producer policy C03A0988 runs before
allocation; a separate consumer policy runs after dequeue, so queue submission
and permission to execute are different facts.

Asynchronous requests return the queue routine's result, including errors.
Synchronous requests wait on manager+12C with mask1, mode21, timeout FFFFFFFF;
their return is a wait-success boolean, NOT the target handler's result.
The worker signals completion after dispatch even if consumer policy declined
the request. Do not call this synchronously from the same consumer task.
The sender nulls its holder before queue submission; send-failure ownership
depends on C036D948, which has not been traced here. Do not assume rollback/free.
Allocation failure and the tested invalid ID51 reach an assertion boundary.

Original ARM experiment:
  .venv/bin/python -B tools/research_dispatch.py
  builds/dispatch-research/report.json
  builds/dispatch-research/disassembly.txt
Executes all 51 original dispatch rows with allowed/refused policy; disabled
producer entries; full request copying; async error propagation; synchronous
wait success/failure; allocation and invalid-ID assertion paths.
OS queue/wait, allocation, logging, consumer policy and business handlers are
explicit modeled boundaries. No scheduler, hardware or recording proof.

Related property infrastructure: C00913F8 validates an index against a domain
count, not a generic property-value clamp. count1 normalizes to index0; count>1
accepts an in-range index or FFFF sentinel. Other tested inputs assert.
C0064580 passes its r2 selector as that index, while preserving its r1 value
separately for C00742F8. Do not infer arbitrary numeric property values are safe
from the selector check. The experiment executes this validator too.

Developer leverage: submission, execution and completion can now be distinguished.
A future read-only event tracer can correlate native requests with the selected
handler and state-policy rejection, rather than treating every successful post
as a successful action. That would support discovery across native operations,
not just a single feature. No tracer is installed or claimed complete.

Next architecture boundary: map C036D948/C036D9C0 queue ownership and the worker's
task identity, then decode producer and consumer policy inputs. Before any live
tracer, establish bounded logging, no pointer retention, caller/task context and
shutdown detachment. Do not issue unknown requests or bypass native policy.
